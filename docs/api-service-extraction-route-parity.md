# API extraction route parity manifest

**Status:** Normative implementation manifest — all 60 rows are implemented and locally verified; live deployment and operational evidence remain required before release.

This manifest is the row-level companion to [`api-service-extraction-plan.md`](api-service-extraction-plan.md). It records every target business operation: the 58 existing API operations (including the shared-vault audit `GET` re-export), plus the recovery-eligibility `GET` and Personal-only workspace-bundle `GET` operations. Hono-derived `HEAD` behavior is tested separately and is not an additional business operation.

**Version rule:** each existing source route `/api/<path>` maps to exactly one canonical API target route `/v1/<path>`. The API origin has no `/api` prefix; `v1` is a fixed version segment. Browser clients use the web-only same-origin proxy path `/api/v1/**`, which maps to API `/v1/**`; SSR, native clients, and the Bun, Node.js, and Vercel adapters use `/v1/**` at the API origin. No unversioned API route alias is implemented.

Every implementation row must additionally link to the source route and existing or newly relocated tests. The implementation may not change the listed authentication policy, response contract, encrypted encoding, transaction boundary, or invariant without an approved plan revision.

The current authentication contract adds a cross-cutting constraint to row 1: browser and installed-PWA requests carry a safe one-time Turnstile token that the API validates before anonymous rate limiting and challenge creation; native requests omit the token and retain the shared PostgreSQL limits. Trusted proxy client-IP handling uses an explicit proxy marker, and missing trusted IPs use a shared unattributed budget rather than bypassing the limit. Request bodies, encrypted blobs, rotation arrays, and ciphertext payloads are bounded before parsing or persistence. The current Shared Vault invitation contract remains client-only: the browser uses a localized `mailto:` draft or copy fallback for the Secure Share Link secret, while the API receives only permitted verifier/package material. These effects must be represented in the relocated transport tests without moving secrets to the API.

## Source and test anchors

- A non-dynamic source row is implemented by `apps/api/src/route-handlers/<path>/route.ts`; `:vaultId` and `:userId` use `[vaultId]` and `[userId]`. The shared-vault audit `GET` operation intentionally reuses the redacted audit reader implementation, while its `POST` operation uses the shared-vault access recorder. The only web route in this boundary is `apps/web/src/app/api/[...path]/route.ts`.
- Historical route-contract anchors were relocated from `apps/web/src/tests/contract` into API-owned route-handler/application suites. Current API anchors include `apps/api/src/app.test.ts`, `apps/api/src/route-parity.test.ts`, `apps/api/src/http/api-http.test.ts`, `apps/api/src/route-handlers/me/route.test.ts`, `apps/api/src/route-handlers/personal-vault/{initialize,destructive-reset}/route.test.ts`, and the API-owned identity/retention/application unit suites. The web `apps/web/src/tests/contract/api-proxy-route.test.ts` covers only the browser proxy boundary.
- `route-parity.test.ts` enumerates all 60 registered `/v1` operations, including the passwordless Account Deletion operations, checks that `/api/v1` is not an API-origin alias, exercises every row through its no-database/auth boundary, and exercises Hono-derived `HEAD` behavior for public reads. Route-handler/application tests cover success, mutation, persistence, and security behavior for the implemented use cases; database integration evidence must run only against an already-approved schema state.
- Historical integration fixtures, repositories, and database tooling are API-owned under `apps/api`; browser anchors remain `apps/web/src/tests/browser/*.spec.ts` and exercise the web/API path. No migration or lifecycle operation is implied by test execution.
- No web-specific test may directly import Prisma or an API route handler; architecture tests enforce the boundary.

## Mandatory review gates

- The source-route mapping, exact status/body/error contract, request schema, response schema, rate-limit policy, repository transaction, and existing test references must be filled for every row before child issues are created.
- Browser proxy, direct native bearer, SSR gateway, and where applicable Bun, Node.js, and Vercel transports must be recorded separately; passing one adapter test alone does not establish parity.
- Every mutation must have a concurrency/idempotency result and a permitted read-after-write or explicit reason why no read exists.
- Every upload/download row must record byte limits, streaming behavior, cache policy, and client-only plaintext/key handling.
- Every delete/reset/purge row must record affected rows, deadlines, restoration behavior, and audit retention.
