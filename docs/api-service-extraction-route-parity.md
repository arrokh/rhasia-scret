# API route and contract inventory

**Status:** Normative API route and contract inventory — all 70 operations are defined by canonical OpenAPI 3.1, generated into the shared TypeScript route manifest and Go/Echo dispatch. Go/Echo is the deployed API runtime. The TypeScript/Hono/Prisma implementation and differential runner have been retired; frozen route, anonymous-boundary, and email fixtures remain historical compatibility baselines, not an active oracle. This manifest and route-count tests do not establish operation-specific success or live deployment readiness. The route table's rightmost source/test anchors record the pre-cutover TypeScript implementation and are historical, not current file locations or a complete Go coverage report. Responsive web/PWA is the sole supported client.

This manifest records all 70 current business operations, including ten operations added after the earlier 60-row extraction snapshot. The retired Hono implementation established implicit `HEAD` behavior for eligible `GET` routes; Go/Echo preserves that transport behavior, which is tested separately and is not an additional business operation. The earlier standalone-extraction plan remains a historical record; the active migration and runtime design is in [`api-go-echo-sqitch-migration-plan.md`](api-go-echo-sqitch-migration-plan.md).

**Version rule:** each API operation has exactly one canonical API target route `/v1/<path>`. The API origin has no `/api` prefix; `v1` is a fixed version segment. Browser clients use the unchanged web-only same-origin proxy path `/api/v1/**`, which maps to API `/v1/**`; SSR uses `/v1/**` at the API origin. The Go/Echo runtime serves this contract on Docker and Vercel. No unversioned API route alias is implemented.

At the original extraction, each row linked to the source route and tests. Those rightmost links are retained as historical provenance; current Go source and replacement-test decisions are recorded in the API retirement review. The implementation may not change the listed authentication policy, response contract, encrypted encoding, transaction boundary, or invariant without an approved plan revision.

The current authentication contract adds a cross-cutting constraint to row 1: when Web is configured with a Turnstile site key and API with its matching secret, browser and installed-PWA requests carry a safe one-time token that the API validates before anonymous rate limiting and challenge creation. API uses only the secret; without it, no token is required and the PostgreSQL-backed anonymous limits still apply. The self-hosted installer enforces the both-or-neither pair. Trusted proxy client-IP handling uses an explicit proxy marker, and missing trusted IPs use a shared unattributed budget rather than bypassing the limit. Request bodies, encrypted blobs, rotation arrays, and ciphertext payloads are bounded before parsing or persistence. The current Shared Vault invitation contract remains client-only: the browser uses a localized `mailto:` draft or copy fallback for the Secure Share Link secret, while the API receives only permitted verifier/package material. These effects must be represented in the relocated transport tests without moving secrets to the API.

## Current source and test anchors

- The canonical OpenAPI source is `packages/api-contract/openapi.yaml`; `packages/api-contract/src/generated-routes.ts` and Go `apps/api/internal/httpapi/operations.gen.go` are generated outputs guarded by `pnpm run verify:api-contract`. Handwritten Go operation handlers live under `apps/api/internal/handler/<context>`. The only Web route in this boundary is the separate Next.js proxy at `apps/web/src/app/api/[...path]/route.ts`.
- Go `apps/api/internal/httpapi/operations_test.go` checks exact generated dispatch for all 70 operations. Go unit, HTTP handler, PostgreSQL integration, golden, and context tests cover selected behavior, authorization, mutation, persistence, and security. The web `apps/web/src/tests/contract/api-proxy-route.test.ts` covers the browser proxy boundary. The 70-operation count is inventory evidence, not proof that every operation has real-stack success coverage.
- `operation-boundaries.json` preserves synthetic anonymous HTTP outcomes captured before cutover and is consumed by Go runtime-composition tests as a compatibility baseline; it is not an active TypeScript comparison. Historical evidence reports 98 authorized requests across 70 unique paths from the retired differential runner on cloned synthetic databases. That scenario suite was not exhaustive and is not rerunnable; rely on current Go, shared-contract, and browser tests for active coverage claims.
- `packages/api-contract/test-fixtures/http-golden.json` contains selected synthetic cross-cutting HTTP examples; `operation-boundaries.json` is a historical compatibility baseline; and `email-golden.json` contains synthetic English email output rendered by Go tests. Separate Go SMTP tests cover both Indonesian and English. These fixtures do not replace operation-specific success tests or disposable database-backed core-flow verification.
- Historical migration fixtures remain under `apps/api/prisma/archive/`; active Go repositories and database tests live under `apps/api/internal`. Browser tests remain in `apps/web/src/tests/browser/*.spec.ts`. No migration or lifecycle operation is implied by test execution.
- No Web-specific test may directly import Prisma or an API route handler; Web architecture tests enforce this boundary.

## Contract maintenance gates

- The source-route mapping, exact status/body/error contract, request schema, response schema, rate-limit policy, repository transaction, and existing test references must be filled for every row before child issues are created.
- Review the browser proxy and SSR gateway against the shared Go contract; Docker and the existing Vercel Go functions must serve the same handler implementation. Passing a generated-route test alone does not establish business or deployment parity.
- Every mutation must have a concurrency/idempotency result and a permitted read-after-write or explicit reason why no read exists.
- Every upload/download row must record byte limits, streaming behavior, cache policy, and client-only plaintext/key handling.
- Every delete/reset/purge row must record affected rows, deadlines, restoration behavior, and audit retention.
