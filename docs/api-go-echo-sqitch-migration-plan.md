# Go/Echo API rewrite and Prisma-to-Sqitch transition: implementation plan and evidence

**Current status:** The Go/Echo API and Sqitch transition described here were merged in PR #329 at `1a549bc3ef3aa8a36b7d681644addeeae0ea1fa5`. This file is retained as a historical implementation plan and evidence record: source paths and “outstanding” items below describe the 2026-11-10 cutover review and may have been superseded. A separately approved follow-up is retiring the TypeScript/Hono/Prisma oracle and resolving SMTP localization; see [`docs/reviews/core-flow-test-review.md`](reviews/core-flow-test-review.md). No production deployment, production database operation, or follow-up merge is authorized by this document.
**Research checked:** 2026-11-10.
**Companion research:** [Go Echo and Sqitch primary-source findings](research/go-echo-sqitch-primary-source-research.md).

## Goal

Replace the TypeScript/Hono/Prisma API implementation in `apps/api` with a Go service using Echo, and replace Prisma Migrate with Sqitch-managed PostgreSQL change scripts.

Treat these as two connected but separate changes:

1. **API rewrite:** move the HTTP runtime, authentication, application workflows, persistence adapters, and operational endpoints to Go.
2. **Migration-tool transition:** make Sqitch the forward migration authority without replaying the existing Prisma migration history or changing business data during the runtime cutover.

The first Go cutover should preserve the existing database schema, stored rows, `/v1/**` HTTP contract, API origin, authorization behavior, and client/server security boundary. Defer unrelated product/schema changes.

## Recommended architecture

```text
apps/api/
|-- go.mod, go.sum
|-- sqitch.conf              Sqitch project settings; no target credentials
|-- cmd/api/                 standalone server entrypoint
|-- api/                     Vercel Go HTTP function adapters
|-- internal/
|   |-- httpapi/             Echo router, middleware, transport DTOs
|   |-- config/              validated server-only environment
|   |-- modules/             bounded contexts and application workflows
|   |-- postgres/            pool and shared transaction helpers
|   `-- .../infrastructure/  context-owned SQL repositories/adapters
`-- db/sqitch/
    |-- sqitch.plan
    |-- deploy/
    |-- revert/
    `-- verify/
```

- Use the latest stable versions available when implementation starts, then pin exact toolchain/module versions (never floating tags). Online checks on 2026-11-10 showed Go 1.27.3, Echo v5.4.4, and pgx v5.11.0; the disposable compatibility fixture passed and cross-built with that toolchain. A later vulnerability review found GO-2026-6859 in Go 1.27.3's standard library, so the repository now pins Go 1.27.4 and the affected x/crypto module is upgraded to its fixed revision. `govulncheck` reports no remaining findings. Local Go 1.27.4 checks and the current Vercel Go handler's local-source Preview build/smoke passed. Vercel's current Go docs say it reads the Go version from the `go` directive in `go.mod`, lets `toolchain` override it, and downloads/caches the selected toolchain; `go.mod` must be at the Vercel project root (`apps/api`). Verify the exact-head Preview with `node apps/api/scripts/verify-git-preview.mjs` after pushing the final clean PR commit. It requires the local SHA to match the open PR head, a successful `Vercel – api-rhasia-scret` commit status, and Vercel metadata proving a GitHub source with the exact branch/SHA in the existing API project and a READY Preview. It then sends a short-lived CLI-issued OIDC token only to `/v1/health` and `/v1/time`, validates the HTTP 200 JSON, and emits a secret-free evidence record. Any later commit requires rerunning the verifier.
- Use Echo as the `net/http` routing/middleware layer with a custom bounded error handler. Preserve middleware order for request IDs, proxy trust, CORS/origin checks, cache policy, logging, authentication, and rate limiting.
- Use a direct PostgreSQL driver/repository layer (recommended starting point: `pgx/v5`) and explicit SQL/transactions. Do not add another ORM by default. Bound per-instance pool size to the existing maximum of five connections unless measured deployment evidence justifies a change.
- Keep bounded contexts under `internal/modules/<context>`. Route handlers validate transport input, invoke a use case, and map typed errors to the established HTTP contract. Do not move crypto, TOTP generation, or plaintext handling to the server.
- Keep `packages/api-client` and the web/PWA implementation in TypeScript. Make `packages/api-contract/openapi.yaml` the canonical OpenAPI 3.1 wire contract for the 70 existing operations, including requests, responses, status/error codes, auth requirements, limits, and reusable headers. Generate the Go Echo v5 server interface/transport types with `oapi-codegen` (`echo5-server`, strict server, and models), and generate the TypeScript route manifest and Go operation dispatcher from the same specification with CI drift checks. Runtime route registration intentionally bypasses oapi-codegen's parameter-binding wrapper: its early query validation can precede authentication and replace established operation-specific errors. Generated routes pass the raw Echo context and path parameters to handwritten handlers, which retain request validation and error policy. Generated code owns transport boilerplate only—not authorization, business rules, transaction boundaries, or error policy.
- Configure strict JSON decoding in Go. Reject unknown fields where current Zod request schemas are strict; enforce the same body, string, array, ciphertext, archive, pagination, and upload limits before expensive parsing or persistence.
- Preserve server-only secrets in validated server configuration. Runtime receives `DATABASE_URL`, never the migration/admin `DIRECT_URL`; only the migration job receives its direct Sqitch target. Do not log credentials, tokens, cookies, request bodies, ciphertext, invitation material, email, or query values.
- Preserve `AUTH_BACKEND=none` as local-only mode: hosted identity, Vault, sync, membership, audit, and recovery operations fail closed, and Tailscale reachability never becomes an application identity. Production still requires an explicit supported backend.
- Preserve the current SMTP safety contract: only ports 465/587; implicit TLS or mandatory STARTTLS; TLS 1.2 minimum; bounded connection/greeting/socket timeouts; certificate validation; one recipient; no file/URL access; and no SMTP message text in logs. Per the user's direction, retain the current English-only email output exactly and do not add locale selection or infer locale from `Accept-Language`. This preserves API behavior but conflicts with the repository's bilingual-surface policy; see outstanding policy conflict.

### Go conventions adapted from the reference API

Use idiomatic Go formatting and package names, `context.Context` for request-scoped repository/use-case work, explicit constructor injection, interfaces at application boundaries, and table-driven tests with named subtests where they improve coverage. Keep related work in focused files and packages; wrap internal failures with `%w` so causes remain inspectable. Use stable structured event names, but never include credentials, tokens, cookies, user data, request bodies, ciphertext, or query values in logs or client-facing errors.

The reference API uses global `handler`, `service`, and `repository` layers, Echo v4, GORM/MySQL, Wire, and common Echo binding/validation. This repository instead keeps its required bounded contexts under `internal/modules/<context>/{application,infrastructure,presentation}`, uses Echo v5 with generated OpenAPI transport, pgx/PostgreSQL and explicit SQL, strict bounded request decoding, and explicit runtime composition. Keep these project-specific choices; do not add Wire or another ORM just to match the reference. Preserve existing API pagination and response/error semantics rather than adopting the reference's new-endpoint cursor-pagination or error-envelope conventions. Log only bounded/redacted event data as required by this repository's security policy.

## Selected port method: contract-first compatibility rewrite

Do not mechanically translate TypeScript files or replace Hono handlers with generated business logic. The old API implementation is the behavioral oracle; the existing HTTP operations are the specification to preserve.

1. Build the OpenAPI 3.1 contract from the current 70-operation manifest, route handlers and Zod validation, client call sites, and existing route/contract tests. Resolve any mismatches before Go implementation. Keep the source TypeScript API available locally during the migration as a comparison oracle, not as a permanent second implementation.
2. Use `oapi-codegen` to generate Echo v5 routing interfaces and transport models. Its official documentation supports OpenAPI 3.1 and Echo v5, but documents limitations for some schema unions; constrain or adapt the spec and inspect generated output. Add explicit Go validation where code generation does not enforce current strict Zod semantics, bounds, cookie behavior, or headers.
3. Implement each bounded context and PostgreSQL repository in Go, then compare old and new APIs against identical synthetic requests and database fixtures. Differential tests run only in local/disposable environments; do not dual-write or mirror production user requests.
4. After every operation group passes parity and core-flow/security tests, cut over the API origin once. Do not maintain per-route fallback to the old API after production cutover.

This is preferred over handwritten duplicated schemas because the web remains TypeScript while the server becomes Go; a shared OpenAPI contract prevents route and DTO drift. It is preferred over generating the whole server because authorization, encrypted-data boundaries, and database transaction semantics need explicit review.

## Sqitch transition and existing database adoption

### Baseline design

Convert the final state of the 26 Prisma migrations into one reviewed Sqitch `init` baseline change, followed by ordinary Sqitch changes for future schema work. Do not translate each historical migration into a deployable Sqitch change. The `init` deploy script must create the complete current application schema from an empty PostgreSQL 16 database. While `init` is the latest deployed API change, its verify script checks a closed-world fingerprint of tables, columns, types, defaults, constraints, indexes, row-security state, extensions, sequences, views, routines, triggers, and policies; the synthetic adoption test separately proves that registration preserves existing application rows. Sqitch runs all deployed verify scripts against the current database, so after a later API schema change is registered, the immutable `init` verifier defers its exact-snapshot check. Every future change's verify script must check the complete post-change application-schema fingerprint and reject untracked objects. Compare all app-owned PostgreSQL objects, including any extensions, sequences, triggers, functions, policies, or grants found during inventory. Explicitly distinguish app schema from Sqitch registry and legacy `_prisma_migrations` metadata.

The baseline is not safely revertible once application data exists. Its revert script must fail closed rather than drop user tables; disposable test-container teardown is the cleanup mechanism for fresh-schema tests. In local disposable PostgreSQL 16 databases, compare app-owned catalog objects produced by the legacy migration chain with those produced by `init`; review any difference and require an equivalent final schema before accepting the baseline. Exclude only Sqitch registry and legacy `_prisma_migrations` metadata from this comparison.

Test existing-schema adoption locally using only a fresh disposable PostgreSQL database: materialize the checked-in schema-only legacy fixture at `apps/api/db/sqitch/test-fixtures/legacy-prisma-schema.sql` (captured from a fresh synthetic PostgreSQL 16 database before the Prisma history was archived), insert synthetic sentinel rows, register `init` with `sqitch deploy --log-only`, verify it, and confirm the application-schema dump and sentinels are unchanged. Do not replay the archived Prisma scripts. `--log-only` records the change without running its DDL and **does not validate the schema**; the wrapper must compare the fixture and fresh Sqitch baseline independently.

**Local baseline evidence (2026-11-11):** A fresh synthetic PostgreSQL 16.15 database was migrated through the checked-in 26-migration Prisma path. The Sqitch `init` DDL is based on that database's schema-only dump, with Prisma migration metadata excluded, so it preserves physical column order that differs from Prisma model field order. Fresh `sqitch deploy --verify` and `sqitch verify` passed. Normalized schema-only dumps from the Prisma and Sqitch databases matched exactly (21 application tables, 49 indexes, 38 constraints). On a separate migrated database, `--log-only` adoption and `sqitch verify` passed; a synthetic sentinel row was unchanged and the before/after schema dumps matched. The fingerprint verifier uses relative column ordinals to ignore internal `attnum` gaps left by historical column drops. A fresh PostgreSQL 16 Testcontainer run also confirmed the verifier rejects synthetic extra sequences, views, routines, triggers, and policies, then passes again after their removal. Every run-owned Compose/Testcontainer container, volume, network, and migration image was removed and verified absent. No persistent or production database was accessed.

Do not create the Sqitch registry or register `init` in production during the Go runtime cutover. If a future production schema change is needed, first perform a read-only schema comparison against `init`; with exact-target approval, register the already-present baseline using `sqitch deploy --log-only --to init <target>`, run `sqitch verify`, and deploy only the new change. If the schema does not match, stop and prepare a target-specific migration. Sqitch registry creation and baseline registration modify the database even though `init` DDL is skipped.

Do not convert 26 historical migrations into changes merely to replay them. Retain the Prisma migration table and old scripts as read-only history until an explicit retirement decision. Archive them under `apps/api/prisma/archive/`, keep Prisma configuration free of a migration path, and do not leave two active migration systems. The current passwordless preflight/seed/verify procedure is historical for databases that have completed it. Any target that has not completed that state needs a separately reviewed, target-specific data migration—not a baseline assumption.

### New migration rules

1. Every new change has deploy, revert, and verify scripts; add a CI check because Sqitch itself warns rather than fails when a verify script is absent.
2. Run `sqitch deploy --verify` and `sqitch verify` on fresh, synthetic PostgreSQL 16 Testcontainers in CI. Verify the baseline on both a fresh install and a synthetic existing-schema adoption fixture.
3. Use expand/contract changes for application compatibility. Only author a revert when it is genuinely safe. For irreversible data changes, document a forward-recovery/backup-restore procedure and make the revert path fail closed rather than imply data can be recovered.
4. Keep Sqitch plan/configuration free of credentials. Use a migration-only, non-pooled direct target derived from `DIRECT_URL` (or the approved equivalent), and validate the URI conversion: Prisma-specific URL parameters such as `schema=public` may not be accepted by pgx/libpq/Sqitch unchanged.
5. Never use a pooled runtime connection for migrations. No operational database migration, Sqitch baseline registration, or administrative operation is authorized by this plan.

### Phase 3 — port bounded contexts in dependency order

Port the API in slices that keep the app compiling and contract-tested:

1. **Identity and HTTP admission:** passwordless challenge request/redemption, cookie sessions/assertions, refresh/revoke, PWA handoff, trusted origin/proxy checks, Turnstile, SMTP, anonymous and authenticated rate limits. 5. **Lifecycle and operational workflows:** retention purge, account deletion/OTP/receipt, database health, shutdown and scheduler command.

For each slice, port unit tests and PostgreSQL integration tests with synthetic data before routing any client traffic to it. Reuse existing tests as behavioral evidence; translate their protected invariants rather than deleting them because the implementation language changed. Preserve authorization and transaction boundaries in the owning context.

- All 70 current API operations, plus the established HTTP/system behavior, remain available at the same `/v1/**` paths with matching request/response/status/header/error behavior.

Account deletion remains committed if completion-email delivery fails. - The browser/PWA contract remains intact: no API-origin `/api/**` alias; cookies and proxy assertions are unchanged; sessions and one-time handoff rules remain secure.
- Passkey recovery proves the existing registration/authentication PRF ceremony and package format end-to-end using synthetic browser credentials. The development-only fake authenticator cannot be enabled in production.
- No TOTP secret, raw QR payload, OTP, Vault key, private key, plaintext vault name/account label, Secure Share Link secret, decrypted archive, request credential, or sensitive body enters server logs, shared caches, analytics, or database persistence.
- Authorization, per-member permissions, rate limits, revisions, invitations, audit redaction, account deletion, and retention deadlines match current behavior and pass concurrency/failure tests.
- Sqitch can create the current schema from empty PostgreSQL 16 and can safely record/verify an already-current synthetic schema without replaying Prisma migrations; sentinel application rows remain unchanged during adoption. Every future Sqitch change has deploy/revert/verify artifacts and CI coverage; baseline revert refuses to drop application data.
- Runtime and migration credentials are isolated; Go API process receives only pooled `DATABASE_URL`, while Sqitch runs in a separate migration-only job with a direct connection.
- Full repository verification passes after the final implementation change, including Go formatting/vet/unit/integration checks, Web, client-core, architecture, build, performance, Chromium browser gates, and the synthetic API k6 suite. A successful local gate does not authorize deployment or persistent database operations.
