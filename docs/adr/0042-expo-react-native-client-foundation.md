# Expo React Native client foundation

- **Status:** Accepted
- **Date:** 2026-08-11
- **Related:** ADR-0035, ADR-0037, ADR-0041
- **Issue:** #96

## Decision

The iOS and Android client is an Expo SDK 57 React Native application with generated native projects under `apps/mobile`. Expo supplies reproducible native configuration and maintained adapters for Keychain/Android Keystore-backed secure storage, linking, localization, lifecycle, camera, clipboard, document, and sharing facilities. The application remains a separate presentation/composition target while consuming the platform-neutral ports and protocol contracts introduced by ADR-0041. Its current hosted scope includes Personal Vault setup/unlock, Authenticator Accounts, Shared Vault access and permissions, Secure Share Links, audit history, archives, and read-only encrypted offline snapshots; it does not implement the browser-only Local Profile/Local Vault.

The initial native authentication transport uses Supabase Auth passwordless email links with PKCE. Production callbacks use verified iOS Associated Domains and Android App Links on the HTTPS origin configured by `EXPO_PUBLIC_WEB_ORIGIN`; a registered custom scheme exists only for development. Supabase sessions persist only through `expo-secure-store`. Application API calls receive the access token at the `BearerTokenTransport` boundary, while the Next.js Supabase verifier accepts either its existing cookie credential or one well-formed bearer credential. A malformed Authorization header fails closed and never falls back to browser cookies. Provider-neutral OIDC remains a server identity boundary and is not a claim that the current mobile UI supports every provider flow.

Indonesian remains the deterministic initial locale and every native surface ships exact Indonesian/English key parity. Native presentation does not import `next-intl`; locale-independent application/domain contracts remain unchanged.

## Security and compatibility

Expo public configuration contains only public service URLs and the Supabase publishable key. It must never contain service-role credentials, OIDC client secrets, TOTP content, OTPs, Vault keys/passphrases, archive keys, Secure Share Link material, private keys, or decrypted content. Session values are never logged, placed in TanStack Query, or persisted outside secure native storage.

Incoming authentication and Secure Share Links are classified without retaining their secret-bearing URL in React state. Existing authorization, admission, revision, rate-limit, audit-redaction, one-time-link, ciphertext, and protocol rules remain server-enforced.

Native Local Vault Snapshots use the existing encrypted offline-bundle contract and receive an additional context-authenticated AES-256-GCM layer at rest. The random 256-bit storage key is kept only in Keychain/Android Keystore through `expo-secure-store`; the encrypted blob is atomically replaced in the application document directory through `expo-file-system`. Missing or malformed key/ciphertext state fails closed. Offline workspaces are explicitly read-only: account mutations are removed, no operation is queued or replayed, while local TOTP generation and explicit native clipboard copy remain available. Online account import parses `otpauth` content and encrypts it locally, sends only the existing context-bound ciphertext contract, then refreshes the authorized encrypted snapshot. QR import requests camera permission only after an explicit action and uses `expo-camera`'s native QR scanner; raw scan data is delivered directly to the client form and is never logged or transmitted before local encryption. Portable Vault archives reuse the shared context-authenticated archive protocol. Native export does not release the archive or key until the existing owner-authorized, rate-limited export audit succeeds; it then writes ciphertext to a temporary cache file only for the `expo-sharing` sheet and deletes it after dismissal, while its key is copied separately. Native import uses the system document picker, decrypts and validates locally, re-encrypts every account for a permitted Personal or Shared Vault, submits only ciphertext through the existing authorized bulk-import endpoint, clears the opened archive immediately after server success to prevent replay if refresh fails, and refreshes the encrypted snapshot.

Shared Vaults are unlocked from the same authorized encrypted bundle. Native presentation uses the server-provided effective account permissions to expose or remove additions and revision-checked deletion, records online Shared Vault account copies through the existing rate-limited audit endpoint, and presents owner-authorized audit history using localized event labels. Secure Share Link creation derives its secret, verifier, and encrypted Vault-key package locally, sends only the verifier/package and recipient metadata to the existing one-time invitation endpoint, and reveals the fragment secret only through the native share sheet; dismissal or share failure attempts immediate invitation revocation before clearing the secret so an unusable live invitation is not intentionally left behind. Verified incoming links retain only the fragment secret in an in-memory ref until the unlocked User Root Key can rewrap the Vault key; redemption remains server-enforced and one-time, and its encrypted snapshot is refreshed after success.

Expo does not imply WebAuthn PRF compatibility. Device-bound unlock/recovery remains unsupported until real iOS and Android hardware validation determines whether an equivalent capability exists; any divergent design requires a separate ADR and explicit user-facing language. Native AppState backgrounding locks the workspace and clears unlocked key material; this is lifecycle protection, not a device-bound recovery mechanism.

Native protocol cryptography composes the shared protocol implementation with maintained, pinned `@noble/ciphers`, `@noble/hashes`, and `@noble/curves` primitives for AES-256-GCM, HMAC, and P-256 ECDH. Argon2id and cryptographically secure random generation use the repository-owned Expo module at `apps/mobile/modules/native-argon2id`, built from the reference Argon2 C implementation and small native iOS/Android adapters. This keeps the memory-hard KDF off the JavaScript thread, clears native password/hash buffers where mutable, preserves the web client's exact Argon2id parameters, and avoids depending on an incompatible experimental package. The upstream wrapper and Argon2 licenses are retained beside the source. Its Android linker emits 16 KiB-compatible LOAD segments for Android 15+ devices, and the owned Android instrumentation test executes the shared Argon2id vector through JNI on an emulator/device. An explicitly opt-in bilingual validation build executes the same native module on iOS Simulator without production material or network requests; distributed builds omit that flag.

The lockfile carries a pnpm-managed compatibility patch for `expo-modules-jsi@57.0.8`. Xcode 26.3 rejects the package's `SWIFT_RETURNS_RETAINED` annotations on `RuntimeScheduler` constructors, and Swift 6's strict-concurrency checker rejects the synchronous JSI bridge's call-scoped raw-pointer captures. The patch removes the invalid annotations and wraps those pointers in an explicitly documented `@unchecked Sendable` holder; it changes no runtime behavior. Remove the patch when an upstream SDK 57 package is compatible with the supported Xcode/Swift toolchain and both native release builds pass without it.

## Consequences

`apps/mobile` `verify` and the root `test:full` gate include strict mobile lint/typecheck/tests, Expo Doctor, and production iOS/Android JavaScript bundle exports. Native release compilation is a separate evidence step using `build:android-native` and `build:ios-simulator`; Android instrumentation and real-device evidence are separate again. JavaScript export or simulator evidence is not proof of hardware capability parity, and physical-device validation remains mandatory before device-bound recovery can ship.
