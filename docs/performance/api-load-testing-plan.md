# Core-flow API load testing with k6

## Purpose and status

This document specifies a safe, repeatable k6 suite for understanding the current API rate-limit and service-capacity behavior through the self-hosted application. It is a characterization plan, not an API SLO or a promise of production capacity. No expected production traffic target or API latency SLO has been established; the initial profile is a bounded pilot, not a forecast. The isolated runner, Compose overlay, browser fixture helpers, and k6 workloads are implemented. Successful local workload evidence now covers returning-Personal-Vault reads and account mutations (B), the first-time hosted flow (A), selected rate-limit boundaries (#251), and Shared Vault invitation/member reads plus separate account mutations (C). The dedicated capacity profile remains unrun; its user-approved target is 11 VUs for 2 minutes, and it still needs a fresh project plus exact-database migration confirmation. Local Docker is the expected internal test mode; a remote generator is not required for this acceptance scope. Every new scenario still requires its own fresh, exact-scope disposable database and migration.

The test order is:

1. **B — Returning Personal Vault user**, the primary repeatable load flow.
2. **A — First-time hosted user**, a low-volume, browser-driven sign-in and setup flow.
3. **C — Shared Vault**, low-volume invitation onboarding plus higher-volume access by existing members.

The implementation must keep detailed browser correctness in Playwright, use k6 for a scalable HTTP workload with a small browser workload, and never target production.

## Verified architecture and current limits

### Authenticated application mutations

ADR-0034 defines PostgreSQL-backed, fixed-window budgets keyed by opaque Application User ID and operation class. The policy is shared across API instances and alternate routes that use the same operation class. Authentication and Application User provisioning happen before the limit check; the check runs before body parsing and domain mutation.

| Operation class                   | Limit |  Window | Relevance to these flows                                              |
| --------------------------------- | ----: | ------: | --------------------------------------------------------------------- |
| `account_mutation`                |   120 |    60 s | Personal and Shared Vault account create/update/delete/restore routes |
| `account_deletion_authentication` |    10 |   600 s | Not exercised; inventory only                                         |
| `archive_export`                  |    10 | 3,600 s | Not exercised; inventory only                                         |
| `archive_import`                  |    10 | 3,600 s | Not exercised; inventory only                                         |
| `audit_event`                     |   120 |    60 s | Shared Vault OTP-card access uses it; excluded from these scenarios   |
| `destructive_mutation`            |     5 | 3,600 s | Not exercised; inventory only                                         |
| `key_material_mutation`           |    10 |   300 s | Personal Vault initialization and other key-material operations       |
| `membership_mutation`             |    30 |    60 s | Secure Share Link/invitation and membership operations                |
| `recovery_authentication`         |    30 |   300 s | Not exercised; inventory only                                         |
| `recovery_mutation`               |    10 |   600 s | Not exercised; inventory only                                         |
| `vault_mutation`                  |    30 |    60 s | Shared Vault creation and other Vault mutations                       |

A denied mutation returns `429 rate_limited` with a bounded `Retry-After`. If the PostgreSQL limiter cannot decide, the request fails closed with `503 rate_limit_unavailable` and a short `Retry-After`.

Each application limiter consumption uses a PostgreSQL transaction and an atomic upsert. The transaction also attempts bounded cleanup of up to 1,000 rate-limit rows expired by more than 24 hours. This cleanup and the per-user/per-operation counter rows are part of the database behavior to observe under load. The shared API Prisma pool is capped at five PostgreSQL connections per process/instance.

### Anonymous passwordless sign-in

Magic-link requests first validate the request and Turnstile, then consume PostgreSQL-backed fixed-window buckets, then persist a challenge and attempt email delivery. Limits are **5 requests per keyed normalized-email bucket** and **20 per keyed trusted-proxy IP bucket per 15 minutes**. If the request has no trusted client IP, it uses a shared unattributed bucket with the same 20-request limit. A rejected request must not send email. These limits are separate from authenticated application mutation limits.

The local self-hosted configuration documents Cloudflare Turnstile testing credentials. The validator still calls Cloudflare's siteverify endpoint, so the low-volume authentication and anonymous-limit scenarios require outbound access; an unavailable provider is a setup failure, not a reason to bypass validation. The E2E session shortcut is enabled only for development; the self-hosted Compose services run production builds, so the load tests must not depend on or enable that shortcut.

The trusted-IP bucket is populated only when the Web runtime trusts forwarding metadata from a configured proxy. The repository's local self-hosted default sets `AUTH_TRUST_PROXY_HEADERS=false`, so requests through the local web origin use the shared unattributed bucket instead. The default local suite can validate that fallback. Testing the trusted-IP branch requires a trusted proxy that strips client-supplied forwarding headers and supplies the verified client IP; k6 must not spoof `X-Forwarded-For` or send the private API proxy credential.

### Runtime and existing test coverage

The supported self-hosted Compose topology contains the web service, API service, PostgreSQL 16, and retention scheduler. PostgreSQL is private to its Compose network. The normal `pnpm selfhosted:*` commands use a fixed project name and preserve the database volume on shutdown; `selfhosted:setup` also applies migrations after confirmation. The load-test harness in [`tools/load-test.mjs`](../../tools/load-test.mjs) instead uses a unique, disposable Compose project and volume. Each project is limited to one load scenario so repeated rate-limit boundary groups necessarily start from a fresh database.

Existing Playwright E2E coverage includes synthetic Personal Vault and Shared Vault workflows. It uses a development-only session cookie and is not a load generator. OTP generation and clipboard writes happen on the authorized client. A Shared Vault account-access/copy action separately sends a redacted `audit_event` request; the selected load scenarios do not perform that action. The load-test target, its web container listener, and callback-oriented unit/contract fixtures use `http://localhost:4000`; ordinary self-hosted development continues to use its separate `localhost:3000` default. A targeted audit found no `localhost:3000` target in the runner, Compose overlay, k6 workloads, or fixture helpers; the only such value in the runner test is a negative case asserting rejection. The load-test implementation files contain no pending-work placeholders. The repository currently has no API latency SLO; initial latency measurements are therefore observational.

## Scope

### In scope

- A throwaway self-hosted Compose stack using the web proxy, API, PostgreSQL 16, and the retention-purge scheduler, plus a test-only local SMTP capture service (Mailpit or an equivalent).
- k6 HTTP requests through the self-hosted web origin's `/api/v1` proxy, covering the web-to-API boundary without placing the private proxy credential in k6.
- A small number of k6 browser VUs for UI journeys and client-only unlock/OTP behavior, alongside scalable HTTP VUs.
- B, A, and C user journeys in the priority order above.
- A full policy inventory and boundary tests for only the anonymous and authenticated policies exercised by those journeys.
- A first bounded ramp of 1, 5, and 10 VUs, with two-minute holds at each stage. Higher ceilings require an explicit operator setting.
- Pin the selected k6 and browser-module versions and include them in every run report.
- k6, container, PostgreSQL, and aggregate limiter evidence, plus deterministic teardown.

### Out of scope

- Any production, preview, or other shared/persistent database or service.
- Sending load through a production SMTP provider or production Turnstile credentials.
- Testing every authenticated policy boundary in the initial slice; recovery, deletion, archive, and other unrelated policies are documented but not boundary-tested.
- Claiming a general capacity number or enforcing an absolute latency SLO before one is established.
- Replacing the detailed Playwright functional suite with k6 browser tests.
- Direct-to-API load as the primary end-to-end path; it can be added later as a diagnostic if measurements require isolation of the API layer.

## Test environment and safety

1. Start a new Compose project with a unique per-run identifier. Use a fresh PostgreSQL volume and the production-shaped web/API images. Do not use the existing `rhasia-scret-selfhosted` project or its volume.
2. Apply only the checked-in migrations to that fresh, test-owned database. The runner must identify the exact project/database before any migration or cleanup operation and require explicit human authorization in the current conversation for that exact disposable database before migrations run. Use the Compose migration profile and dedicated `apps/api/Dockerfile.migration` runner (`deploy-passwordless-migrations.mjs`) so the staged preflight, identity seed, verification, and guarded cleanup remain intact; do not run migrations implicitly when starting the stack or k6. Do not inherit or reuse `DATABASE_URL`, `DIRECT_URL`, or credentials from any existing `.env` or `.env.prod`; generate per-run PostgreSQL, proxy, authentication, and retention-scheduler credentials plus URLs that point only to the run-owned PostgreSQL service. Keep any required environment file outside the repository with owner-only permissions and remove it during teardown. Migration, scenario-preflight, and execution failures tear down the exact run by default unless `--preserve-on-failure` is explicitly selected; teardown revalidates the recorded Docker-context fingerprint before deleting run resources and fails closed on context drift.
3. Configure passwordless auth with localhost origins, the documented Turnstile testing pair, and a local SMTP catcher. Require SMTP TLS and per-run SMTP credentials; trust only Mailpit's run-generated certificate for the SMTP client. Before `up` reports readiness, run a transport-only synthetic email smoke through the API runtime's environment-binding and SMTP-sender path, verify the expected message in run-owned Mailpit, then clear and verify the mailbox is empty. This does not create a passwordless challenge or bypass authentication. Keep the SMTP catcher's inspection endpoint bound to loopback; remote forwarding is out of scope for this internal, same-machine acceptance, and no remote-runner variant is required. Store captured messages only in ephemeral container storage, clear them after redemption, and expose no test-only authentication bypass or public mail UI.
4. Bind the published web and SMTP inspection ports to loopback by default. The test runner must require an explicit target tied to the current run's Compose project and reject production/Vercel origins, public addresses, and mismatched targets. Keep `WEB_ORIGIN` and `AUTH_APP_ORIGIN` on localhost/127.0.0.1 for the documented Turnstile testing pair. The synchronized disposable-database policy requires a local Docker context; same-machine local Docker is expected, and separate-runner/remote-generator mode is intentionally unsupported rather than an acceptance blocker. Any future remote tunnel would require a separately approved design with strict SSH host-key checking and forwarding limited to loopback ports 4000 and 8025; never expose the test stack publicly or use a production/shared Docker host.
5. Use synthetic identities on reserved test domains, synthetic Vault/account labels, and client-generated or otherwise non-sensitive opaque ciphertext fixtures. Never place plaintext TOTP configuration, Vault secrets/keys, generated OTPs, Turnstile tokens, magic-link tokens, cookies, or request bodies in k6 output, logs, analytics, or committed files.
6. Keep magic-link fragments and session cookies in memory only. The k6 setup phase may pass authenticated test sessions to VUs in memory, but must not write them to files or include them in the summary. Redact dynamic identifiers in metric tags to prevent high-cardinality output.
7. By default, remove the exact per-run Compose project and its database volume after the run, including on failure. Preserve a failed stack only with an explicit opt-in. Retain sanitized test results only under ignored `test-results/load/`.
8. Do not run migrations or load tests against the existing self-hosted development stack as part of validating the harness. Running the full load profile is a separate, explicit operator action after the isolated stack and safeguards are verified.
9. Install the pinned runner with `mise install k6@0.57.0` and run commands in that tool environment, for example `mise exec k6@0.57.0 -- pnpm loadtest help`. Ensure OpenSSL is available to create the ephemeral, owner-only Mailpit TLS certificate. Install the repository-managed browser binary if needed with `mise exec -- pnpm --filter @rhasia-scret/web exec playwright install chromium`; the runner uses that Chromium executable for k6 browser scenarios.

## Workload scenarios

### B — Returning Personal Vault user

Use a pool of ten synthetic users with distinct Application User IDs and already initialized Personal Vaults. Prepare their sessions through the real local passwordless flow and local mail catcher; do not use the development-only E2E cookie or a production-mode bypass. Generate/prepare the pool before the measured stages so authentication setup does not contaminate the measured returning-user workload.

The primary workload is read-mostly: authenticate with an existing session, retrieve the current user/workspace and encrypted account data through the web proxy, and validate response status and bounded response structure. For this Personal Vault scenario, OTP generation and copying stay client-side; do not model the OTP value or clipboard write as an API request. Run account create/update mutations as a separate workload so they can be measured and attributed to `account_mutation`; use ten distinct sessions, rotate session selection across iterations, create a fresh account per iteration, and send one create/update pair per second. This keeps even a single active VU well below the 120-per-user/60-second budget so expected limits and revision conflicts do not obscure service capacity.

Run a small browser workload during HTTP load to verify the real page remains usable and that unlock/OTP generation still occurs client-side. When co-scheduled, keep browser VUs at 10% or less of total planned VUs where practical; run them separately for the 1-VU stage or when that ratio is not meaningful. Keep the detailed workflow assertions in Playwright.

### A — First-time hosted user

Run at low volume through the real passwordless UI flow: request a magic link, retrieve it from the local SMTP catcher, redeem it, initialize a Personal Vault, add a synthetic Authenticator Account, unlock the Vault in the browser, and confirm an OTP is rendered locally. Check correctness without recording the OTP, passphrase, magic-link token, or ciphertext body.

The email capture service is only for the isolated test stack. Requests use the documented local Turnstile testing pair, and each magic-link request obtains a fresh widget token kept in memory only. The flow is intentionally low-volume; separate boundary cases validate the 5/email and 20-request network-side buckets (the shared unattributed bucket in the default local configuration, or the trusted-IP bucket only behind a verified proxy). Do not interpret this scenario as SMTP-provider or Turnstile capacity testing.

### C — Shared Vault

Use a small browser workload for owner-created Shared Vault onboarding: create the Vault, create a Secure Share Link/invitation, redeem it as a synthetic recipient, and open the Vault. The link secret remains in the client fragment/memory only and must never be copied into k6 logs or result files. Do not click an account to copy its OTP in the capacity workload; that separate Shared Vault account-access action emits an `audit_event` request.

For higher-volume load, prepare existing owner/member relationships and exercise authorized Shared Vault reads. Exercise permitted account mutations separately with ten distinct owner sessions and ten distinct Shared Vaults; rotate the owner/vault pair per iteration while creating a fresh account, at one mutation per second. Keep onboarding and established-member access as separate scenarios so one-time invitation semantics and membership rate limits do not distort read-capacity measurements.

## Rate-limit boundary tests

Run each anonymous boundary group against a fresh isolated database state, separate from the ten-user session-pool setup. The network-side bucket (trusted IP or shared unattributed fallback) is shared by requests in that environment, so a fresh project prevents setup sign-ins from consuming the boundary-test budget. Obtain a fresh token from the local Turnstile widget for each request, use it only in memory, and do not assume a token can be reused or bypass site verification. Use the local mail catcher to assert that limited magic-link requests do not trigger delivery.

Test the following core-flow policies:

| Boundary                                                                                                                                                | Expected outcome                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Same normalized email: 5 accepted requests in a 15-minute window, then the next request is limited                                                      | `429 rate_limited` with `Retry-After`; no email for the rejected request                                                                                                                      |
| Local default shared unattributed bucket: 20 accepted requests across distinct synthetic emails in a 15-minute window, then the next request is limited | `429 rate_limited` with `Retry-After`; no email for the rejected request                                                                                                                      |
| Trusted-IP bucket (only behind a trusted test proxy)                                                                                                    | 20 accepted requests for one verified client IP in a 15-minute window, then the next request is limited; the next request returns `429 rate_limited` with `Retry-After`, and no email is sent |
| Personal Vault initialization/key-material mutation budget                                                                                              | First 10 authenticated operation attempts in 5 minutes pass the limiter; the next attempt is limited                                                                                          |
| Account mutation budget across applicable Personal/Shared routes                                                                                        | First 120 authenticated operation attempts in 60 seconds pass the limiter; the next attempt is limited                                                                                        |
| Shared Vault creation (`vault_mutation`)                                                                                                                | First 30 authenticated operation attempts in 60 seconds pass the limiter; the next attempt is limited                                                                                         |
| Secure Share Link/membership mutation                                                                                                                   | First 30 authenticated operation attempts in 60 seconds pass the limiter; the next attempt is limited                                                                                         |

Use the same Application User for all attempts in each authenticated boundary case; otherwise the per-user budget is not being tested. Where applicable, test that alternate routes sharing one operation class consume the same budget (especially Personal and Shared account routes). Boundary probes may use a request body that fails validation after authentication so the limiter is exercised without repeating a domain mutation; the first N responses may therefore be validation errors, while the N+1 response must be the limiter's `429` before body parsing. The key-material group splits attempts across identity registration, identity rotation, and Shared Vault key rotation; account attempts split across Personal and Shared Vault routes; vault attempts split between Shared Vault creation and rename; membership attempts split across link creation, member-permission defaults, and member overrides. Each group keeps the same Application User, and the k6 checks verify each route's expected validation error and `rate_limited` for rejections, rather than treating status alone as proof of admission. Expected `429`s in these boundary scenarios are successes; a `429` during the normal B/C load workload is unexpected. Database failure is not an expected boundary outcome and must be reported as fail-closed `503 rate_limit_unavailable`.

## Load profile, thresholds, and stopping

### Initial profile

- Warm up the disposable stack and verify its health checks before starting k6.
- Run the returning-user HTTP scenario at 1, 5, and 10 VUs, holding each level for two minutes and ramping gradually between levels. Its one browser smoke iteration starts during the 10-VU stage; browser resource use is not comparable to HTTP VU capacity.
- Run first-time sign-in, Shared Vault onboarding preparation, and rate-limit boundary scenarios as low-volume browser journeys. Shared Vault reads and account mutations remain separate measured scenarios.
- The owner-approved capacity profile allows the k6 generator and stack on the same machine only with the `capped-local-v1` Docker Compose resource caps below. Reports must say `same-machine`; do not present these results as separate-host or general capacity. A dedicated SSH stack host remains supported when available.
- **The numeric limits below remain provisional, not acceptance-ready.** The first successful returning-Personal-Vault B run collected 27 Docker snapshots per service; those are the first representative workload peaks for that scenario, not evidence for all scenarios. The user requires each service cap to be no more than 2× its measured workload usage. Use the remaining B mutation, A, C, rate-limit, and capacity runs to validate/calibrate service limits before treating them as final.
- Require an explicit configured ceiling before exceeding 10 VUs. Capacity mode accepts 11–20 VUs with `--confirm-high-vus` equal to the exact ceiling, and requires `--duration` from 1 second through 10 minutes. Do not implement an unbounded breakpoint ramp.

### Bounded Compose resources

The load-test overlay runs one container per service and enforces per-container caps via Docker Compose. The current Mac has 14 logical CPUs/36 GiB host memory; OrbStack reports 14 CPUs/15.7 GiB for its Linux engine. The runtime service limits total 6.25 CPU and 7.75 GiB, leaving engine headroom while k6 runs on the Mac. The one-shot migration container has its own cap and does not run concurrently with capacity measurement.

| PostgreSQL (`db`)    |       2.0 |        3 GiB |
| API                  |       1.5 |        2 GiB |
| Web                  |       2.0 |        2 GiB |

### Correctness and stop conditions

- An unexpected `4xx`, `5xx`, timeout, authorization failure, stale-revision conflict, or rate-limit response in normal B/C traffic is a correctness failure. A limiter boundary test classifies its expected `429` separately from service errors.
- Stop a stage if a required web/API/PostgreSQL health check fails, PostgreSQL becomes unavailable, or unexpected HTTP failures exceed 1% for 30 seconds. That 1% is a protective abort criterion—not an allowed error rate, pass threshold, or service SLO. Also stop if the operator observes resource exhaustion or the k6 generator itself is saturated; a saturated generator invalidates the measurement.
- Record p50/p90/p95/p99 latency, throughput, request failures, checks, and dropped iterations. Do not set an absolute latency pass threshold until the service has an agreed SLO. Report the self-hosted host specification and whether k6 ran on the same machine.

## Evidence and reporting

For each run, retain a sanitized report under `test-results/load/<run-id>/` containing:

- k6 summary and structured metrics for HTTP latency, throughput, error/status classifications, checks, and browser Web Vitals where collected;
- sanitized lifecycle stop reason, fixed high-level failure phase, and allowlisted browser-helper phase detail; do not retain child stderr, raw errors, request/response bodies, cookies, emails, tokens, or credentials;
- stage configuration, VU count, duration, test scenario, git commit, k6/browser-module versions, runner placement/network path, machine specifications, and the exact Compose service resource caps;
- timestamped k6-process and, for separate runners, SSH-tunnel CPU/resident-memory samples, plus Docker CPU/memory snapshots for run-owned services, sampled peak usage for the one-shot migration container, and PostgreSQL connection/activity snapshots;
- the existing one-minute aggregate application rate-limit metrics.

The application limiter metrics are process-local aggregates by operation and outcome, not a global counter; interpret them alongside k6 results and container/database observations. Each process emits a completed minute window only when a later limiter event arrives; there is no guaranteed periodic or shutdown flush, so the final partial window may be absent. Do not retain raw request/response dumps, cookies, emails, Turnstile or magic-link tokens, ciphertext bodies, OTPs, passphrases, or private key material. Commit the plan and scripts only; run reports remain ignored and local.
