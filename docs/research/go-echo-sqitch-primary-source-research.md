# Primary-source research: Go Echo and Sqitch

**Checked:** 2026-11-10
**Purpose:** Assess the requested `apps/api` Go/Echo rewrite and replacement of Prisma migrations with Sqitch. This is framework and migration-tool research, not a production deployment or database assessment.

## Findings

### Echo and Go runtime

- Echo v5 is a Go HTTP framework built around method/path routing, route groups, middleware, and a configurable central error handler. Route groups can share prefixes and middleware; handler and middleware errors flow to `HTTPErrorHandler`. A migration must install a custom error handler rather than inherit framework defaults if it is to preserve this API's bounded `{ "error": "..." }` responses and redacted server errors. ([routing](https://echo.labstack.com/docs/routing), [middleware cookbook](https://echo.labstack.com/cookbook/middleware/), [error handling](https://echo.labstack.com/next/guide/error-handling/), [recovery middleware](https://echo.labstack.com/next/middleware/recover/))
- Echo's v5.4.4 module declares Go `1.25.0`; its release notes report validation with Go 1.25 and 1.27. On the research date, the official pages showed Go 1.27.3 as the latest stable Go release, Echo v5.4.4, and pgx v5.11.0. A disposable fixture using Go 1.27.3, Echo v5.4.4, OpenAPI 3.1, and `oapi-codegen` v2.8.2 generated Echo v5 strict-server code and passed `go test`, `go vet`, native `go build`, and Linux/amd64 cross-build. This validates local toolchain/framework/codegen compatibility, not Vercel's hosted runtime. Recheck versions at implementation and pin them in the project toolchain and module files. ([Go downloads](https://go.dev/dl/), [Echo v5.4.4 release](https://github.com/labstack/echo/releases/tag/v5.4.4), [Echo releases](https://github.com/labstack/echo/releases), [Echo `go.mod`](https://github.com/labstack/echo/blob/master/go.mod), [pgx releases](https://github.com/jackc/pgx/releases), [Echo README](https://github.com/labstack/echo/blob/master/README.md), [v5 API changes](https://github.com/labstack/echo/blob/master/API_CHANGES_V5.md))
- Vercel documents its Go runtime as **Beta on all plans**. File-based functions live under `/api` and export an `http.HandlerFunc`. The current docs say Vercel reads the Go version from the `go` directive in `go.mod`, lets a `toolchain` directive override it, requires `go.mod` at the Vercel project root, and downloads/caches a toolchain the first time it is used. With no version declared, Vercel uses its latest supported Go version. The docs do not publish a supported-version matrix or explicitly confirm Go 1.27.3; the exact selection is configurable online, but its successful build must be proven with a custom-branch build. Echo uses the compatible standard `net/http` handler contract, which still merits that deployment spike. ([Vercel Go runtime](https://vercel.com/docs/functions/runtimes/go))
- The official `go-webauthn/webauthn` project documents typed WebAuthn PRF extension support, including PRF registration support and assertion-time evaluation. This is a plausible Go dependency for the current passkey-recovery boundary, not evidence by itself that the app's exact ceremony, validation, and encrypted package protocol will interoperate. Pin a reviewed release and prove that with synthetic browser tests before committing to the full port. ([project](https://github.com/go-webauthn/webauthn), [package API](https://pkg.go.dev/github.com/go-webauthn/webauthn/webauthn))
- For the cross-language API contract, `oapi-codegen` added OpenAPI 3.1 support in v2.8.0 and documents an Echo v5 server generator (`echo5-server`) with strict-server generation. It also documents limitations in some OpenAPI 3.1 schema patterns. This makes it a strong candidate for generated Go transport models/interfaces, not for business logic or authorization. Inspect generated code for the actual spec and retain explicit validation for current strict Zod rules. ([v2.8.0 release](https://github.com/oapi-codegen/oapi-codegen/releases/tag/v2.8.0), [Echo v5 generator](https://github.com/oapi-codegen/oapi-codegen/blob/main/docs/echo5-server.md), [configuration](https://github.com/oapi-codegen/oapi-codegen/blob/main/docs/configuration.md), [project](https://github.com/oapi-codegen/oapi-codegen))

### Sqitch and PostgreSQL

- A Sqitch project records ordered changes in `sqitch.plan`; each change has authored deploy, revert, and verify scripts. PostgreSQL is a supported engine (`pg`), with scripts executed through PostgreSQL tooling. Sqitch is a change-management tool, not an ORM or a schema-to-code generator. ([init](https://sqitch.org/docs/manual/sqitch-init/), [add](https://sqitch.org/docs/manual/sqitch-add/), [plan](https://sqitch.org/docs/manual/sqitch-plan/), [PostgreSQL tutorial](https://sqitch.org/docs/manual/sqitchtutorial/))
- `sqitch deploy --verify` runs verify scripts during deployment, but deployment verification is not the default. `sqitch verify` runs available verify scripts; a missing verify script warns rather than failing. Repository CI should therefore enforce a verify script for every planned change. ([deploy](https://sqitch.org/docs/manual/sqitch-deploy/), [verify](https://sqitch.org/docs/manual/sqitch-verify/))
- `sqitch deploy --log-only` records planned changes as deployed without running their deploy scripts. Sqitch documents this for adopting a database changed by other means. It does **not** prove that the database matches the plan, so the target schema must be inspected and independently verified before or immediately after logging the baseline. ([deploy](https://sqitch.org/docs/manual/sqitch-deploy/))
- Sqitch does not infer inverse SQL. Reverts are authored scripts, and deployment failure handling assumes a change is atomic; therefore, a revert script is not a guarantee that irreversible data changes can be undone. Prefer expand/contract changes, make only genuinely safe changes revertible, and define an explicit forward-recovery or backup-restore path for destructive changes. ([deploy](https://sqitch.org/docs/manual/sqitch-deploy/), [revert](https://sqitch.org/docs/manual/sqitch-revert/), [PostgreSQL tutorial](https://sqitch.org/docs/manual/sqitchtutorial/))

## Verification performed (2026-11-10)

- Installed Go 1.27.3 through mise for the local check; the repository itself still has no Go pin (`.mise.toml` omits Go and the existing shell default is 1.25.1).
- In a disposable `/tmp` fixture, pinned `toolchain go1.27.3`, Echo v5.4.4, and generated a minimal OpenAPI 3.1 Echo v5 strict server with `oapi-codegen` v2.8.2. The Vercel-shaped `http.HandlerFunc` adapter passed `go test`, `go vet`, native `go build`, and `GOOS=linux GOARCH=amd64 go build`.
- A first fixture attempt used Echo v4-style `echo.Context`; compilation correctly failed. Echo v5 requires `*echo.Context`; the documented/generated signature compiled. This is a useful porting guardrail.
- Hosted verification used a temporary custom branch (`infra/verify/vercel-go-runtime-20261110`, commit `553a6f4`) in the existing API Vercel project. Vercel reported a Preview deployment as Ready and built `api/go-runtime-verification` as a Go function. The protected endpoint returned `{"go":"go1.27.3","echo":"v5.4.4"}`. This proves the selected toolchain and Echo v5 handler execute on Vercel's Go Beta runtime; it does not prove full API behavior, cold-start/connection characteristics, or production readiness. The initial build attempts showed that Go is unavailable to the custom Node build command and that the normal deployment-config preflight requires preview environment values; the temporary probe build therefore runs the existing Vercel bundle build and lets Vercel compile the Go function separately. The main branch remains Node/pnpm configured. `vercel curl` created one project-level automation-bypass secret to query the protected endpoint. The user chose to leave it in place; it is not branch-scoped. No production database or migration was accessed.

## Repository implications (inspection and recommendations)

This section records repository state at the 2026-11-10 research snapshot; see the implementation follow-up below for later changes and current status.

- The repository had 70 API operations in `packages/api-contract/src/index.ts`, while the route-parity document still described 60 at that time. The implementation branch has since reconciled [`api-service-extraction-route-parity.md`](../api-service-extraction-route-parity.md) against the executable manifest and OpenAPI contract.
- The current API is Hono/TypeScript with Bun, Node, and Vercel adapters. Its database layer is Prisma/PostgreSQL. The Prisma schema defines 21 models, and the repository contains 26 Prisma migration directories. The current API separately owns passwordless browser sessions, PWA handoff, passkey recovery/PRF, Turnstile, SMTP, rate limiting, audit, retention, encrypted-vault persistence, and account deletion. These counts and features come from the checked-in source; they do not prove that every deployed database is at the same schema revision.
- The main branch's tracked `apps/api/vercel.json` remains Node/pnpm oriented: it rewrites `/v1/**` to TypeScript handlers, configures `api/index.ts`, `api/health.ts`, and `api/time.ts`, installs the pnpm API package, and runs the Vercel build script. The temporary probe branch added one Go function and a branch-only deployment exception; it was not merged. Vercel deployment metadata and project-protection state were inspected through the authenticated CLI; Vercel environment-variable values were not inspected.
- **Recommendation:** treat the Go HTTP/runtime rewrite and migration-tool transition as related but separate workstreams. Preserve `/v1/**`, the 70-operation contract, database schema, and existing rows for the initial runtime cutover. Consolidate the final state of Prisma's history into one Sqitch `init` baseline; test fresh install and synthetic existing-schema adoption locally. Do not register or deploy that baseline to production during the runtime cutover. At a future production schema change, verify the existing schema, obtain target-specific approval, log the already-present `init` change without running DDL, verify it, then deploy only the new change. Keep Prisma's migration table and old scripts as read-only history; do not replay those migrations against an already-provisioned database.
- **Recommendation:** use an API-local Go module, Echo over `net/http`, OpenAPI 3.1 as the wire contract, `oapi-codegen` for Echo v5 transport interfaces/types, a PostgreSQL driver/repository layer, and Sqitch scripts. Keep business rules and authorization hand-written, the web API client/TS workspace functional, and client cryptography/TOTP generation outside the server. The user confirmed that one Go/Echo implementation should replace Bun/Node API runtimes in both Vercel and self-hosted Docker deployments.
- **Deployment risk:** the user selected the existing API Vercel project and accepted Beta. The custom-branch probe confirms that `go.mod`'s `toolchain go1.27.3`, Echo v5.4.4, Vercel's Go function routing, and region `sin1` work for a minimal handler. It does not validate the full API, database connections, cold starts, deployment rollback, or production environment. Keep the Node/pnpm main-branch config until the complete Go implementation is ready. Do not create a second Vercel project; production deployment remains separately authorized. The temporary preview verification created a project-level automation-bypass secret with `vercel curl`; the user chose to leave it in place.
- **Email behavior decision:** the user selected preserving the existing English-only SMTP output. This matches the rewrite's behavior-parity scope but conflicts with the repository's policy requiring every production surface in English and Indonesian; it must not be described as localization-complete until that policy conflict is resolved.

## Implementation follow-up (2026-11-12)

- A shared synthetic fixture now compares status, body/error, and stable headers for every anonymous boundary across the current TypeScript reference runtime and composed Go runtime. This is boundary evidence, not a claim that every operation has its own successful cross-runtime request vector; operation-specific handler, repository, and browser tests cover authorized behavior and persistence.
- Disposable run `b96f739a66ef80e8` deployed and verified Sqitch on PostgreSQL 16.15, passed Go database tests and the real-Go browser gate (33 smoke, 8 E2E, 13 PWA), and confirmed Go `/v1` traffic. Teardown verified all run-owned resources were absent. A fresh root `env -u CI mise exec -- pnpm run test:full` also passed on commit `1e1891e`, with Testcontainer and Sqitch image cleanup verified.
- A security scan found GO-2026-6859 in Go 1.27.3's standard library; the repository pin and Docker builders were upgraded to Go 1.27.4. `govulncheck` also reported GO-2026-5932 in `golang.org/x/crypto/openpgp`, which is not reached by this API; the module graph was upgraded to the fixed revision rather than suppressing the finding. The pinned vulnerability scan now reports no findings.
- Added pinned Go vulnerability and license checks, weekly Dependabot Go Modules updates, and Go CodeQL extraction. The established `CodeQL JavaScript and TypeScript` status-check context remains unchanged while its analysis now also includes Go.
- The API Vercel config relies on function auto-detection and omits a custom Go build command because Vercel runs custom build commands before the Go function builder. Production configuration is validated at handler initialization; health/time remain database-independent. A local-source Preview built the tracked Go handler configuration and returned HTTP 200 for `/v1/health` and `/v1/time`. Current-head Git Preview acceptance is verified by `node apps/api/scripts/verify-git-preview.mjs`: it requires the successful exact-SHA `Vercel – api-rhasia-scret` commit status, follows its Vercel dashboard link, verifies the existing project plus matching Git source and READY Preview target, and probes only those two database-independent routes with a short-lived Vercel CLI development OIDC token. The secret-free report is attached to the exact commit as `Manual Preview Smoke (exact-head)`; any later commit requires rerunning the verifier. See the migration plan for exact scope and limits.
